### M4.2 BRAW contact sheet thumbnails (time-boxed spike first) ✅ SPIKE DONE 2026-06-12 — implementation deferred, metadata-only tiles retained
Blackmagic offers no lightweight official CLI. Spike (max 1 day): evaluate (a) ffmpeg builds with BRAW decode patches, (b) Blackmagic RAW SDK sample binaries (`braw` extract tools ship with the free SDK) and (c) shelling to DaVinci Resolve if installed, mirroring the REDline pattern (optional tool, graceful metadata-only fallback).
**Spike output:** a written recommendation in this file. If a viable path exists, implement behind the same detect-or-fallback pattern as REDline with tests using a fixture sidecar + mocked extractor. If not, close the item with rationale and keep metadata-only tiles.

**Spike findings (2026-06-12):** No option reproduces the REDline pattern (detect a prebuilt, on-disk binary and shell to it), so no implementation lands now. Each path evaluated:

- **(a) ffmpeg with BRAW decode patches — rejected.** ffmpeg has no native BRAW support. The only community route is the `adinbied/ffmpeg-braw` fork (built on a reverse-engineered 2019 patch), which is self-described as semi-broken: output is dark and green-tinted, corrected only by approximate gamma/offset filters, not real gen-5 colour science. It also requires a custom ffmpeg build linked against the BRAW SDK. Wrong on both quality and distribution friction for a preview tile.
- **(b) Blackmagic RAW SDK — viable in principle, but not REDline-shaped.** The SDK is free, cross-platform and fully documented; frame extraction is `IBlackmagicRawClip::CreateJobReadFrame(frameIndex)`, demonstrated by the SDK's `ExtractFrame` sample. Critical difference from REDline: REDline ships as a *prebuilt executable* inside REDCINE-X PRO at a known path, so we only detect and call it. The BRAW SDK ships `ExtractFrame` as *source* that must be compiled with Xcode against `BlackmagicRawAPI.framework`. The free Blackmagic RAW Installer installs the framework but no CLI extractor. There is nothing on disk to detect, so the graceful detect-or-fallback model does not apply without us first building and bundling a native helper — which is signing/notarisation/native-build work that belongs in M7.1, not a 1-day spike.
- **(c) DaVinci Resolve shell-out — rejected.** External scripting (the `ExportCurrentFrameAsStill` path) requires Resolve **Studio** (paid); the free version blocks scripting entirely. Even on Studio it means launching the full app `-nogui`, importing each clip to a timeline and rendering a still — far too heavy for contact-sheet thumbnails and gated behind a licence we cannot assume DITs hold.

**Recommendation — keep metadata-only BRAW tiles for now; defer previews.** The existing `make_braw_tile` + `parse_braw_sidecar` path already yields rich metadata (resolution, fps, ISO, WB, camera, duration) from the `.sidecar`/`.xml`, which covers the practical DIT need. **Future path when previews become a priority:** build a tiny standalone `brawextract` helper from the free BRAW SDK `ExtractFrame` sample, bundle + codesign + notarise it as part of the M7.1 DMG packaging, then wire it behind the exact REDline pattern — a `check_braw_extractor()` detector (helper on PATH or in the app bundle) feeding `extract_frames_braw()`, with the current metadata-only tile as the fallback when absent. Tests at that point use a fixture `.sidecar` plus a mocked extractor, mirroring the R3D tests. No code or test changes this session; suite unchanged at 1209 non-GUI tests.

**Recommended design: ship logs to a shared Google Drive folder via the rclone remote every user already has.** Local stays the source of truth (custody logs must exist even offline); a background "log shipping" step uploads new files after each operation and on app launch.
